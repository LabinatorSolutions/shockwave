# CLAUDE.md — settings sections (`src/renderer/settings/`)

Every Settings page. `SettingsModal.tsx` (one level up) is the host; each section here is listed in `SETTINGS_SECTIONS` (`../constants.ts`) and wired into the modal's NAV.

Read `src/renderer/CLAUDE.md` first for the app-wide UI conventions (Tailwind + shadcn, tokens, button hierarchy, the section/dialog templates). **This file is the settings-only policy**: when a value saves, how credentials are handled, and what each section owns.

**The modal gates every page except Companion and Updates on `companionOnline`** (`UNGATED_SECTIONS` in `SettingsModal.tsx`) — the live feed's reachability signal, pushed from main. While it's false the Companion page is forced and the other nav items are disabled ("Connect to your server first"). The feed is the single gate because every other page reads/writes through the *stored* connection, which is exactly what the feed exercises; the Companion page's own probe (`api:test`) is diagnostics for the human — what's wrong: unreachable / bad key / cert awaiting approval — and never drives the gate. (A successful probe kicks the feed's retry in main so the gate follows without waiting out the backoff.) The gate is modal-scoped; `App.tsx` has no full-app block, it just reads settings at boot.

## When a setting saves — one rule, no Save buttons

An audit found six different save models across fourteen sections, so these are now fixed:

- **Text / password / number inputs commit on BLUR**, via `useCommitField` (`useCommitField.ts`). Never write per keystroke: each keystroke is a round-trip to the companion, and anything with a side effect re-fires it too. The GitHub PAT hit this first (typing a token did ~90 writes *and* ~90 sync-engine restarts, against 90 half-tokens); the AssemblyAI key hit it a second way, where each write re-armed the "is this key usable?" check and a stale failure landing last left the Test button dead until you left the page. `useCommitField` also **flushes on unmount**, which is what makes having no Save button safe — closing the modal mid-edit can't drop the value.
- **Credentials use `useCredentialField`** (same file), never `useCommitField('')`. Same blur rule, three differences the generic hook can't express: there is no stored value to follow (main strips it), an empty draft means *unchanged* rather than *cleared* — so an empty commit is a no-op, because clearing a box cannot delete a key — and **the draft resets once committed**, which is what brings the dots back. Leaving that last part to each caller is exactly what happened, and they disagreed: GitHub and Companion reset by hand, while Voice and Agent Chat passed a constant `''` to `useCommitField`, whose resync effect keys on `[value]` and so never re-fired. Their typed key sat in the box until the section unmounted — same field, two behaviours, depending on which page you were on.
- **Toggles, dropdowns, comboboxes and sliders commit on change** (sliders on `onValueCommit`). There's no partial state to protect.
- **Everything goes through the section's `on*Change` prop → `persistSettings`.** Never call `window.api.settings.write` from a section: it skips the Saving/Saved badge and leaves `settingsRef` stale, so a later diffed save computes its patch against a value the server already moved past. (Cron's timezone did exactly this.) The per-workspace sections are the deliberate exception — `TemplatesSection`, `DailyNoteSection`, `WorkspaceSkillsSection` persist via `workspaceSettings:update` (`.shockwave/workspace.json`), not global settings.
- **No Save buttons.** A button in Settings means an *action* — Telegram's Connect (registers a webhook), Agent Secrets' Add, Workspaces' Add, Advanced's Rebuild, the Companion cert Trust. Not "write this form down." Companion used to have Save *and* Test, and Test said "Connected." while storing nothing — the button that reported success was the one that persisted nothing.
- **A validate/verify step must never be the only thing that saves**, and must not be required to save. A Verify/Connect button is fine — it's an action — it just can't be load-bearing for persistence. Companion is the worked example: fields store on blur, **Connect** probes, **Approve** trusts the certificate. Storing is not connecting, and neither Connect nor page-open can grant trust (see "Companion TLS" in `src/main/CLAUDE.md`). Editing either field drops the status row back to "not connected" — this page gates every other page, so it must never show a green line for details that have since changed.
- **Concurrent commits need a request guard.** Blur two fields in a row and two checks are in flight; without a monotonic request id the *last response* wins rather than the newest request. `CompanionSection`, `VoiceSection`, and `useVoiceInput` each carry one.

## Credentials

- **Credential fields are WRITE-ONLY** (`credentialField.ts`). The renderer never receives a credential value — main strips every one before the settings object crosses IPC and substitutes a presence flag (`hasPat`, `hasProviderKey`, `hasVoiceKey`), so a field with something stored renders as dots and one with nothing stored reads `Paste your key` — the placeholder is the only thing that can carry that, since the box is always empty on render (`credentialPlaceholder`). There are no Show buttons; they could only ever reveal what you had just typed. Which fields these are is declared once in `agent-core/credentials.ts` — see the root `CLAUDE.md`.
- Two guards against the obvious hazard, because a write-only field means the cache holds no value to re-send: **the renderer never sends an empty credential** (`../settingsDiff.ts` drops it), and the companion no longer deletes a credential merely absent from a save. Without both, editing an unrelated field — a sync interval — would delete your GitHub token.
- **Clearing the box cannot remove a stored key.** Removal is its own call (`removeCredential` in `credentialField.ts` → the `settings:deleteCredential` IPC, which re-checks the path against `agent-core/credentials.ts`'s `isDeletableCredential` in main before writing the empty string that drops the row) behind a `destructive` Remove button, shown only once something is stored. Deleting is an explicit act on both sides of the boundary, not an inference from an empty field.
- **Every credential box is a `CredentialRow`** (`CredentialRow.tsx`), and its **actions go BELOW the input, never beside it**. Beside was the old shape and it made the field's width a function of state: the buttons are conditional (Remove only once something is stored, Test only for openai-compatible) and their labels grow mid-action, so the GitHub PAT measured 280px empty, 186px with a token stored, and 153px while Verify said "Verifying…" — it moved under the cursor as you used it. Reserving a slot can't fix that either: "Verifying…" + "Removing…" is 216px of the 360px measure. The row takes its width from its container and **never** from a per-call-site class — that's what keeps the six equal. A dialog hosting one sets `className="sm:max-w-[408px]"` (= 360px content + `p-6`) so it matches the settings measure; the Agent Secrets dialogs were 464px before. Never wrap a credential in `InputGroup` — with no addon it's a no-op, and Telegram's had an *empty* inline-end addon that silently ate 8px of text column.
- **Placeholders are format examples, never lookalikes for a real value.** `github_pat_…`, `123456:ABC-DEF…`, `https://203.0.113.10`. Companion's key hint was `••••••••`, which a masked input is indistinguishable from — so pasting a key looked like it had done nothing.
- **The dots clear on focus** — `credentialPlaceholder(saved, focused)`, with the focus state owned by `CredentialRow` so no call site knows about it. Chromium keeps a placeholder visible while an empty input is focused, and this box is *always* empty, so clicking into a stored key changed nothing on screen and the field read as locked; backspace reinforced it, there being nothing to delete. Then typing one character replaced forty dots with a single bullet — which looks exactly like having wiped the key down to one character, at a moment when nothing has been written at all. Focused-and-stored therefore says `Paste a new key to replace`: clearing the dots is the feedback, and the wording answers the question an empty box raises. Blur restores them, because by then the draft has committed and reset.

### Verifying a credential

A credential page's **primary button checks the key** (GitHub → Verify, Agent Voice → Verify, Agent → Test, Companion → Connect) — see the button-hierarchy rule in `src/renderer/CLAUDE.md`.

> **Agent Voice carries THREE primaries — one Verify per vendor row — and that is the rule holding, not bending.** The "exactly one primary per page" rule assumes one credential per page; Voice lists every vendor, each with its own key. What the rule is really protecting is *the page's main action is unmistakable*, and here that action is "check a key" three times over. Promoting one of three would be arbitrary, and demoting all three to `outline` leaves the page with no primary at all — which is what it briefly shipped as.
>
> **Test microphone stays secondary (`outline`).** It answers a different question, not a lesser one: Verify is about a KEY, Test microphone is about the MICROPHONE — the hardware, the OS permission, and the path through whichever vendor the mic is assigned to. They used to be one button doing both badly. The original reasoning still decides the hierarchy: nothing on this page means anything until a key is known good.

Three things every credential check has to get right, all of them learned from a bug:

1. **Wait for the in-flight save.** Main resolves the key from the companion, not from what's on screen, so a verify that doesn't await the blur-triggered write checks the *previous* key. Clicking the button is itself what blurs the field, so that ordering is the normal case, not a corner. Each of the three parks the save promise in a `savingRef` and awaits it — `VoiceSection` inside `runVerify`, `GitHubSection` inside `onVerify`, `AgentChatSection` inside `handleValidate`. This became non-optional when the draft started resetting on commit: there is no longer a typed value to send alongside, so the stored one is the *only* thing being checked.
2. **Invalidate on edit.** A green check beside a key that has since been typed over is actively misleading — typing bumps the request id and drops the row back to idle.
3. **Removing is not failing.** Remove runs the bare re-check (so dependent UI updates) but must not publish its verdict, or deleting a key would paint a red "not configured" under a field the user just chose to empty.

`VoiceSection` also shows what to do when **one credential feeds several capabilities**. `voice:verifyKey(slug)` reports per JOB rather than pass/fail, and the results are distinct UI:

| Result | Shown as |
|---|---|
| key refused outright (`ok: false`) | `ErrorMessage` |
| a job that passed | green `✓ transcribe` / `✓ microphone` / `✓ speak` |
| a job that failed on its own | **muted `✗` plus the vendor's reason**, never red |

**That last row is the whole point, and it is deliberately not red.** A Deepgram key created with the default `usage:write` scope transcribes and speaks perfectly and cannot mint a streaming token — Member is behind an "Advanced" toggle — so it is *good* for two jobs out of three. Reporting "rejected" is false and sends the user to replace a key that works. It is also **actionable now**: the Microphone assignment can be pointed at another vendor, which is the whole reason that assignment exists.

Verify used to BE the token mint, reasoning that AssemblyAI ships no key-check endpoint so the cheapest real request is the check, and that this app only ever used the streaming product. **Both premises died with the second engine.** AssemblyAI still works exactly that way — one credential, one capability, so the mint remains the whole answer — while Deepgram is asked two questions (`GET /v1/auth/token`, which any scope can call, then the grant). Verify also calls **`notifyVoiceConfigChanged()`**, which re-mints in every mounted `useVoiceInput` — this page's Test microphone (gated on the streaming token specifically, so it must grey out in the middle row) *and* the chat composer's mic. It replaced a per-caller `recheck` that only this page ever called, which is why fixing a rejected key left the composer's mic dead until restart. See "Voice input" in `src/renderer/CLAUDE.md`.

## The sections

- `CompanionSection.tsx` — the companion connection every other page depends on: URL (plaintext) + API key via `window.api.settings.apiRead()` / `apiWrite()` / `apiTest({url, apiKey})`. `apiRead` returns only `{ url, hasApiKey }` — the key never comes back to the renderer (it's `safeStorage`-wrapped in main). A successful test also shows the companion's version and runs `apiCheckVersion`; `companion-older` renders an "Update companion" row opening `CompanionUpdateDialog`. **Copy on this page is deliberately short** — the certificate-approval panel is the only text a user must actually weigh, so the surrounding field descriptions were trimmed to let it stand out rather than compete, and the self-signed caveat is explained by that panel in context instead of up front.
- `GeneralSection.tsx` — theme mode, hide-line-numbers, the file-tree quick-access panel, timezone. It was `AppearanceSection` until the timezone landed on it: that field is app-wide (schedules, run times, the agent's date), it had been parked on a Cron page for as long as the desktop ran its own scheduler, and when that page went it needed a home that wasn't about display. A page called Appearance couldn't hold it honestly. **Timezone sits last** — it's set once during companion setup and then never again, while theme and editor display are what people come back to change.
- `WorkspacesSection.tsx` — the workspace list (open / rename / remove / per-row sync switch / set-up-here). "Add workspace" opens `AddWorkspaceDialog`.
- `GitHubSection.tsx` — PAT (encrypted at rest on the companion) + `sync:verifyPat`, sync interval, `sync:checkGit` presence check. None of it is per-workspace: one account, one engine, one binary.
- `AddWorkspaceDialog.tsx` — the one way to add a workspace. **The folder is asked FIRST**, because it decides what's left to ask: `workspace:inspectFolder` classifies it as `clone` (already a checkout — the repo is known, so only a name is needed), `empty` (the Create new / Clone existing choice appears), or `occupied` (refused). That's why there's no "adopt existing folder" mode to hunt for — it's just what happens when you pick a folder that already is one. Links straight to the GitHub section when no PAT is set.
- `VoiceSection.tsx` ("Agent Voice") — voice in BOTH directions, in two groups. **Listen**: a provider dropdown (AssemblyAI / Deepgram / ElevenLabs) + that vendor's key + Verify (this page's one primary) + "Test microphone" (secondary — it exists mainly to trigger Electron's one-time mic-permission prompt where the user expects it; see "Voice input" in `src/renderer/CLAUDE.md`). **Speak**: a shorter provider dropdown + a voice picker fetched live from the vendor, with a Play button for the ElevenLabs preview. Plus the per-workspace **Telegram replies** mode.

  **Providers are the object; jobs are assigned to them.** Two groups: **Providers** lists every vendor unconditionally with its key, Verify, Remove and what that key can do; **What uses what** assigns the three jobs — Microphone, Transcription, Speech — plus the mic test and the voice picker.

  > **The page used to be organised the other way and that was the bug.** A key box lived inside each direction group, but a key is a property of the VENDOR, so one Deepgram key rendered three different ways depending on unrelated dropdown state (a box under Listen, a box under Speak, or the sentence "same key as above") and appeared to vanish when a dropdown moved. Worse, a vendor you weren't currently using was invisible: `voiceKeys` holds three, the old page drew at most two, and a stored key you'd stopped using could be neither seen nor removed. Listing every vendor always fixes both — nothing moves, and what is stored is what is on screen.

  Five things about it are deliberate. **Three assignments, not two** — the microphone is separate because a key can be permitted to transcribe and not to stream, and on Deepgram that is the default key (`transcription.micProvider`; unset ⇒ whatever transcribes). **The lists are per job**, from `agent-core/voiceProviders.ts` — AssemblyAI cannot synthesize, so a single "voice provider" choice would either hide a vendor people already use or quietly speak with somebody else's account. **A keyless vendor is listed and marked `(no key)`, never filtered out** — filtering makes the list mysteriously short with no clue what would lengthen it, while naming the gap turns the dropdown into an instruction. **The page resolves through `voiceConfigOf` + `providerForJob`, the same functions the consumers use** — it holds `hasVoiceKey` rather than key values, and `voiceConfigOf` folds those flags in, so Settings cannot show one answer while the agent uses another. **The voice list is fetched, not hardcoded**: a voice you cloned exists only in your account. Nothing in the page branches on a provider string; the table does.
- `AgentChatSection.tsx` — see **"The Agent Chat page"** below; it's long enough to need its own section.
- `AgentSecretsSection.tsx` — two credential kinds. **Static tokens** (`Add token`): `{name, description, token}`, edited inline. **OAuth connections** (`Connect account`): a provider `Select` (from `oauth:listPresets`) + a dependent **Setup** `Select` of curated scope bundles (`preset.setups`, e.g. "Gmail — read") that fills the always-editable scopes field + client id/secret; submit persists the connection then kicks `oauth:startConnect` (system browser). Reconnect/expired reuse the stored config, so re-auth needs no re-typing. Rows show a `StatusBadge` + Connect/Reconnect + Disconnect. Names unique case-insensitive; all secret material encrypted at rest **on the companion**. The OAuth connect/disconnect writes tokens on the companion, so the section calls `onReload` (→ `useSettings.reloadAgentSecrets`) to refresh status **without** re-persisting (which would clobber the companion-written tokens).
- `WorkspaceSkillsSection.tsx` ("Manage Skills") — per-workspace: import a `SKILL.md`-bearing folder into the workspace, and toggle each **built-in** skill on/off for this workspace (the `builtinSkills` map, absent ⇒ enabled, via `workspaceSettings:update`). Replaces the old global/workspace skills tabs.
- `TemplatesSection.tsx` / `DailyNoteSection.tsx` — per-workspace template folder; daily-note format + target folder. Both persist via `workspaceSettings:update`.
- **There is no cron page.** Scheduled runs execute on the companion, and its remaining knobs are that server's env (`CRON_ENABLED`, `CRON_REFRESH_SCHEDULE`) — nothing the desktop can write. The run time limit moved OUT of env to `codingAgent.maxRunMinutes` and lives on the Agent Chat page, since it bounds Telegram turns as well and is a thing a user actually wants to change. The page that used to be here outlived the desktop scheduler by holding one unrelated field (the timezone, now in General) and two links back to the panel that linked to it. Job definitions live in `<workspace>/cron.json`; the whole in-app surface is `CronModal` (the clock in the rail). Don't add one back to expose a server env var.
- `TelegramSection.tsx` — connect/disconnect the Telegram bot + a workspace picker for where its messages run (`telegram:*`; the companion owns it), plus **`transcription.echoTelegramTranscript`** (default off), which decides whether the companion posts a voice note's transcript back as `🎤 "…"` before running the turn (`api/src/telegram/webhook.ts`). It's a `transcription.*` key on the *Telegram* page because it describes bot behaviour, not transcription — the key transcribes either way. So this page writes through `onTranscriptionChange` and must spread the whole slice: that setter REPLACES the renderer's copy, and a bare `{echoTelegramTranscript}` drops the sibling fields, making Agent Voice read as if nothing were configured until main's next `settings:changed` push. `onTelegramChange` has the same rule for the same reason — spread both levels.
  Also **`telegram.chatNotice`** ("Catching up"): whether the bot lists the chats that moved while you were away before answering, how many, and how stale the chat has to be. **One setting with two parameters, not three settings** — the numbers sit inline in the checkbox's own description sentence, because "Shows up to `3` newer chats when the one you're returning to is over `24` hours old" is the only arrangement where the labels aren't restating the sentence. The boxes show the **effective** value (`resolveChatNotice`), not the stored one, since every field is optional and an empty box beside "over ___ hours old" describes nothing; the stored object keeps its unset fields unset so nobody-chose-24 stays distinguishable from you-chose-24. The defaults live in **`agent-core/chatNotice.ts`**, not here — the companion resolves the same object, and a second copy is how this page comes to say 24 while the bot waits 48 (`tests/chatNotice.test.js`). Blur-commit via `useCommitField`, with the value clamped through the same resolver on the way in.
- `UpdatesSection.tsx` — app updates (`useAppUpdate`), and **the page the update pill points at**, so it carries the whole story rather than just a check button: running version, phase, what's new, and ONE primary slot filled by the top action for the phase (Check → Download → Restart). **Check keeps a second button — outline, beside Download — but only while the phase is `available`.** That's the one phase where a re-check both means something and is permitted: `runUpdateCheck` in main returns early once we're `downloading` or `ready`, since a re-check would walk the phase back to `available` and lose the Restart button, so a Check offered there would be a control that does nothing. Without the second button there was no way to re-poll a pending update short of restarting the app. Only Check disables while a check is in flight — the download decision has nothing to wait for. It renders `ReleaseNotesDialog` and is the only place to undo a snoozed version — dismissing the toast is otherwise an invisible, permanent setting. Nothing here downloads or installs on its own (see "App updates" in `src/main/CLAUDE.md`). It is also **exempt from the companion gate** along with the Companion page: it's the one page that talks to GitHub rather than that server, and gating it would send anyone whose companion is away to a page about a different problem.
- `AdvancedSection.tsx` — maintenance actions (e.g. rebuild the link cache).

## The Agent Chat page

The page holds two unrelated things — **which model the chat runs on**, and **how the agent behaves when it runs on its own** — which is why it needs headings and why it isn't two pages. A second nav row would split the model from the runs that use it, and the setup badge (`BADGE_KEY_FOR_SECTION`) plus every deep link key on the one `agent` section.

**Top group, "LLM":** provider, model, and a **per-provider API key map** (`codingAgent.providerKeys`, a `MAP_KEY` in `../settingsDiff.ts`, so a whole map travels on save), plus reasoning level (`agent:listThinkingLevels`) and, for openai-compatible, a Base URL, a context window, and an endpoint check (`agent:validateConnection`). The system prompt isn't editable here — it's assembled from the workspace's `SOUL.md` + the helper (see `agent-core/CLAUDE.md`). Provider + model lists come from `agent:listProviders` / `agent:listModels`.

**Below it, four headed groups.** They were one unheaded run of eight numeric fields, which is how a memory budget ended up sitting next to a git-retry count with nothing to say they were unrelated. The grouping is by *what the number is about*, and each heading carries a one-line `description` (a `SettingsGroup` prop) that says the half the fields would otherwise each repeat:

| Group | Fields | Why these, and not others |
|---|---|---|
| **Memory** | `memoryInterval`, `memoryCharLimit`, `userCharLimit` | one trigger + two budgets over one pair of files. The group line names `MEMORY.md` / `USER.md` and says both load into every chat, so no field has to. |
| **Self-improvement** | `reviewInterval` | its own group **even at one field** — see below. |
| **Waiting for you to finish** | `backgroundQuietMinutes` | the one number the two groups above SHARE, so it sits after both rather than inside either. |
| **Unattended runs** | `maxRunMinutes`, `maxFixAttempts` | both bound turns the companion takes without you. Confirmed server-only: `cronRun.ts`, `backgroundRun.ts`, `telegram/webhook.ts` are the only readers. |
| **Working files** | `checkoutPoolSize`, `scratchTtlDays` | disk the agent works in. |

Two of those placements are load-bearing:

- **Memory and Self-improvement are adjacent but never merged.** They are separate processes with separate triggers, separate counters and separate prompts (see the terminology list in the root `CLAUDE.md`), and a shared heading would read as one feature with two numbers. Being one field is not a reason to fold Review into its neighbour — the thing that needs explaining is what a review run *is*, and that explanation is the group.
- **"Waiting for you to finish" is a third group and not a field in either of them.** It genuinely applies to both, so putting it in one would read as that pass's own number, and duplicating it would be one setting drawn as two boxes. It sits *after* both because it can only be explained in terms of runs the reader has just met. What it buys is the difference between a finished turn and a finished conversation: the running flag clears the moment the agent stops talking, so without it a run can open a chat while the user is composing their next message.
- **`scratchTtlDays` is NOT under "Unattended runs"**, even though it looks like server housekeeping: `src/main/main.ts` sweeps with it at desktop boot as well (`api/src/sweeper.ts` is the other reader). "Unattended runs" was the name this whole block carried once and was dropped for exactly that inaccuracy; it is correct now only because it no longer covers this field.

**Unset defaults and the two commit shapes.** Every field here can be blank, and blank means *unset* — the consumer falls back. `maxRunMinutes` ⇒ 30, `maxFixAttempts` ⇒ 3, `scratchTtlDays` ⇒ 7 (`agent-core/scratchSweep.ts`, shared with the companion, which is also where "pinned chats keep theirs" comes from), `checkoutPoolSize` ⇒ 2, `reviewInterval` / `memoryInterval` ⇒ 10, `backgroundQuietMinutes` ⇒ 10, `memoryCharLimit` / `userCharLimit` ⇒ 2200 / 1375.

- **`checkoutPoolSize`, `reviewInterval`, `memoryInterval`, `backgroundQuietMinutes` take the explicit-blank commit** (`next === '' ? undefined : Number(next)`) because **0 is meaningful** for all four — it disables the queue, the review pass, the memory pass, and (for the last) removes the wait rather than switching anything off. The shorthand would map "0" to unset, i.e. back to the default, the opposite of what was typed.
- **`memoryCharLimit` / `userCharLimit` take the shorthand** (`next ? Number(next) : undefined`) — the opposite, deliberately. 0 is not a meaningful size, a store that can hold nothing fails every write with an error the agent cannot act on, and `clampLimit` in `agent-core/memoryStore.ts` refuses it anyway. Blank-or-zero ⇒ unset is the field agreeing with its consumer.

**Labels name the subsystem rather than reading as prose** — **Agent Run Max Minutes**, **Git Fixer Max Attempts**, **Scratch Pad Max Days**, **Warm Checkouts Kept**, **Review Interval**, **Memory Interval**, **Memory Max Chars**, **User Profile Max Chars** — a deliberate break from the rest of Settings, so a user who reads a key name in the docs can find the field.

**Numeric inputs use `NUMBER_FIELD`** (`SectionUI.tsx`, or `NUMBER_FIELD_WIDE` for up to six digits), sized to the value rather than the 360px measure; a full-width box for "30" reads as somewhere to type a sentence. **They must be wrapped in a plain `<div>`.** `Field`'s vertical variant carries `[&>*]:w-full`, which compiles to a child selector on the parent and so outranks any width class on the input — tailwind-merge never gets a say, and neither does `!`. A width set directly on the input is silently ignored, which is what had happened to General's "Items per list": it declared `w-24` and rendered at 360px. The wrapper absorbs the rule and the input inside is free.

The page's own subtitle says provider keys are encrypted **on the companion**, because they are — `codingAgent.providerKeys` is a `SETTINGS_CREDENTIALS` entry (`agent-core/credentials.ts`) and lands in `secret_value`. It said "on this machine using your OS keychain" for a while, which is true of the *companion's* URL and API key (`safeStorage` in main) and of nothing on this page.

---

`SectionUI.tsx` is the shared scaffolding (`SettingsSection` / `SettingsGroup` / `SettingsDivider`, 360px measure, `wide` for entity lists). `SettingsGroup` takes an optional **`description`** — one line under the heading, for when the *group* is the unit that makes sense and its fields don't individually. Reach for it instead of repeating a shared clause in three `FieldDescription`s; that repetition is how field descriptions grow into paragraphs. `FolderCombobox.tsx` is the workspace-relative folder picker.

The modal's title-bar shows a small `Saving…` / `Saved` / `Save failed` badge driven by `saveStatus` in `App.tsx` (`persistSettings` increments an in-flight counter so overlapping writes don't flash `saved` early). The save badge fades back to idle 1.5s after the last write completes.
